# Issue #15・#17 検証記録（make doctor と、ホストでのコミット）

日付: 2026-11-21。基準コミット: `33939cc`（main）。対象: [Issue #15](https://github.com/tomohiroJin/devcontainer-python/issues/15)（`make doctor`）と、[Issue #17](https://github.com/tomohiroJin/devcontainer-python/issues/17) のうち、ホストからコミットしたときにフックで失敗する件。親は [Issue #13](https://github.com/tomohiroJin/devcontainer-python/issues/13) です。

使い方は [README](../README.md) の「環境の確認（make doctor）」と「コミット前フック (prek)」にあります。ここには、決めたことと、検証の結果を記録します。

実装のあと、フックと `make doctor` のそれぞれを、別の検証者が「欠陥を探す」目的で、2回検証しました。見つかった欠陥を受けて、どちらも設計を改めています。経緯は「敵対的検証での指摘と対応」にあります。以下の「決めたこと」と「確かめたこと」は、2回目の対応のあとの内容です。

## コミット前フック

### 変更前の問題

`make hooks`（`prek install`）が作る `.git/hooks/pre-commit` は、`prek` を呼び出します。`.git` はホストとコンテナで共有しているため、ホストでのコミットでもこのフックが動きます。ホストに prek がなければ、すべてのコミットが失敗しました。prek を入れても、Ruff と mypy がなければ失敗しました（モブプログラミングで起きた問題です）。

### 決めたこと

- **フックの本体を、このリポジトリで管理します**（[scripts/git-hooks/pre-commit](../scripts/git-hooks/pre-commit)）。`make hooks`（[scripts/git-hooks/install.sh](../scripts/git-hooks/install.sh)）が、`.git/hooks/pre-commit` にコピーします。
- **検査をするかどうかは、「Dev Container の中かどうか」で決めます。** イメージにだけあるファイル（`/etc/devcontainer/bashrc`）の有無で判断します。
  - 中: 検査を実行し、失敗したらコミットを止めます。`requirements.txt` と版が違っても実行し、その旨を表示します。
  - 外（ホスト）: 検査を省いて、コミットを通します。ホストに道具があるかどうかは見ません。
  - ホストでも検査したい人は、`git config hooks.devcontainerRunOnHost true` で有効にできます。
- **利用者のものには、手を付けません。**
  - `core.hooksPath` は、どの階層の設定も変更しません。この設定があると Git は `.git/hooks` を使わないので、フックは動きません。その場合は、`make hooks` と `make doctor` が知らせます（1回目の対応では、このリポジトリの設定に `core.hooksPath = .git/hooks` を書き込んでいました。相対パスのため、`git worktree` とサブモジュールで検査が無効になり、利用者自身の設定も上書きしていました）。
  - 自分のフックかどうかは、ファイルの2行目の決まった文言で判断します。それ以外の `pre-commit` は、利用者のものとして退避し、`make unhooks` で戻します。シンボリックリンクには、書き込みません。
- **登録されているフックは、コピーです。** リポジトリのフックと違う場合は、コミットのたびにその旨を表示します。自動では置き換えません。置き換えると、チェックアウトしているブランチのスクリプトを、確認なしに実行することになるためです。
- **検査は `prek run` で実行します。** `prek install` が生成するフックは、prek の内部用のコマンド（`hook-impl` と、スクリプトの版番号）を呼びます。公開されているコマンドだけを使うことで、prek の更新でフックを作り直す必要がなくなります。
- 検査は、Dev Container 内の `make pre-commit` と、プルリクエストの CI（`python` ジョブの `make pre-commit`）でも行われます。CI を必須チェックにする設定は、[Issue #20](https://github.com/tomohiroJin/devcontainer-python/issues/20) に残っています。**それまでは、ホストでコミットした未検査の変更を止めるのは、CI の結果を見てからマージする運用です。**
- Issue #17 の案 (b)（ホストから、コンテナ内の検査を呼び出す）は採用していません。コンテナの名前の特定や、起動していない場合の扱いが、ホストの環境ごとに変わるためです。

#### 残っている性質

- **`make hooks` は、そのとき作業ツリーにあるフックをコピーします。** 信頼できないブランチをチェックアウトした状態で `make hooks`（または、コンテナのリビルド）を実行すると、そのブランチのフックが登録され、そのあと、どのブランチでも、ホストでのコミットでも動きます。チェックアウトしただけでは、何も実行されません。`.git` はコンテナから書き込めるため、コンテナ内で信頼できないコードを動かせば、同じことは別の方法でも起こせます。README に、信頼できないブランチで `make hooks` を実行しないよう書いています。
- **`core.hooksPath` を設定している人は、コミットのときの検査が動きません。** 上のとおり、設定を変えないことを優先しました。

## make doctor

### 決めたこと

- **イメージの検査とは分けます。** `scripts/check_devcontainer.sh` は、イメージが正しく作られたかを CI で確かめます。`make doctor` は、人や起動のたびに変わるもの（Git の設定、認証、フック、リモート）を確かめます。
- **設定を読んで推測せず、Git に実際にやらせます。**
  - 名前とメールアドレス: `git var GIT_AUTHOR_IDENT` と `GIT_COMMITTER_IDENT` が成功するか（設定の階層、`includeIf`、`author.*`・`committer.*`、環境変数のどれで決まっていてもよい）。Git が自動で決めた値かどうかは、`user.useConfigOnly` を付けて確かめます。
  - 署名: このリポジトリの設定のまま、`git commit-tree -S` でコミットのオブジェクトに署名できるか。コミットは作らず、フックも動きません。オブジェクトは、一時的な場所に書きます。
  - 認証情報: `git credential fill` に push 先の URL を渡して、認証情報を取得できるか。ヘルパーの並びや打ち消し（空の値）、ホスト・パス・利用者名ごとの設定は、Git が解釈します。
- **何も変更しません。** 特に、認証ヘルパーには「取得」だけを頼みます。
  - Git は、認証に成功するとヘルパーに「保存」を、失敗すると「消去」を頼みます。接続の確認で利用者のヘルパーを使うと、診断しただけで、保存済みの認証情報が消えたり、別の保存先に書き込まれたりします（2回目の検証で見つかった欠陥です）。
  - そのため、接続の確認では、利用者のヘルパーを使いません（`-c credential.helper=` で打ち消します）。先に取得した認証情報を、「取得」にだけ答える一時的なヘルパーで渡します。認証情報は、本人だけが読める一時ファイルに置き、確認のあとすぐに消します。
- **push と同じ接続先を確かめます。** push に使うリモートと URL（`pushRemote`・`remote.pushDefault`・`pushurl`・URL の読み替え）は、Git に決めさせます。push 用の URL がいくつもあれば、すべて確かめます。接続のときに URL がもう一度読み替えられないように、その URL 自身への読み替えを一時的に指定します。
- **入力待ちで止まらないようにします。** 認証情報とパスフレーズの入力は、受け付けない設定（`GIT_TERMINAL_PROMPT=0`、`GIT_ASKPASS`・`SSH_ASKPASS` を何も返さないコマンドにする）で実行します。入力を求めるプログラム（askpass）が設定されている場合は、実行せずに、「push のたびに入力が必要」と知らせます。
- **外部のコマンドには、制限時間を付けます。** GNU の `timeout` は使わず、自前の見張りで打ち切ります（`timeout` は macOS になく、Ctrl-C への反応も遅れるためです）。打ち切るときは、子プロセスも含めて止め、止め終わるまで待ちます。
- **表示は、すべて伏せる処理を通します。** 行を表示する関数（`ok`・`info`・`warn`・`fail`・`hint`・`detail`）が、表示の直前に伏せます。設定の値そのものは、表示しません。
- **コンテナの作成時には、自動で実行しません。** VS Code がホストの Git の設定をコピーする前に実行されると、誤った結果が出るおそれがあるためです。
- **Dev Container の外では、ツールの版と整形を確認しません。** ホストにはツールがないのが普通で、あっても版が違うためです。
- **push の権限は、GitHub に HTTPS で接続していて、`gh` で認証している場合だけ確認します。**

### 確かめたこと

イメージの検査が、一時的なリポジトリと、一時的なホームディレクトリで確かめます。期待する表示（`ok`・`info`・`warn`・`FAIL`）と、終了コード（`FAIL` のときだけ 1）の両方を確かめています。

| 分類 | 確かめている状態 |
| --- | --- |
| 準備ができている状態 | `warn` と `FAIL` がなく、終了コード 0 |
| 秘密を表示しない | メールアドレス、認証情報、ヘルパーのコマンドに含まれるトークン、ホームディレクトリ、URL の認証情報とクエリ文字列、SSH のリモートのユーザー名、リモート名とブランチ名に含まれるトークンやメールアドレス、`gh` が返すトークン、署名のエラーに含まれる鍵の持ち主の名前。伏せる処理そのものに、各種の秘密（ASCII 以外や、不正な UTF-8 を含むメールアドレスも）を通す。`git@` とホスト名は残る |
| ホームディレクトリ | `HOME=/` や、`#` と `&` を含むパスでも、表示が壊れない |
| 認証情報 | 関数の形のヘルパー（VS Code が使う形）は `ok`。何も返さないヘルパー、ホストにしかないヘルパー、ヘルパーなしは、`github.com` で `FAIL`、他のホストで `warn`。打ち消してから足した設定（`gh auth setup-git` のあとの形）は `ok`。リポジトリのパスごとの設定は `ok`。別の利用者の認証情報しかなければ `FAIL`。askpass があれば `warn`（askpass は実行しない）。止まったヘルパーは、制限時間で止め、プロセスを残さない。ホスト名は大文字と小文字を区別しない |
| 名前とメールアドレス | ないと `FAIL`。作者だけで、コミットする人が決まらない場合も `FAIL`。環境変数、リポジトリの設定、`author.*`・`committer.*` で決まる場合は `ok` |
| 署名 | リポジトリの設定で有効にした署名が失敗すると `FAIL`。リポジトリの設定の鍵で SSH 署名できると `ok`（リポジトリには何も書き込まない）。パスフレーズ付きの鍵は `warn`（15 秒以内に終わること）。タグの署名の失敗も `FAIL`（直し方に、タグの設定を示す）。スマートカードがない場合のエラーは `FAIL`。確認中に、グローバルの `core.hooksPath` のフックが動かないこと |
| フック | 未登録、`prek install` のフック、登録済みのフックが古い、実行権限がない、別の `core.hooksPath` は、それぞれ `warn` |
| リモート | SSH 形式で鍵がないと `FAIL`。ssh が使う鍵のファイル（空白を含むパス）があれば `info`。エージェントの鍵、ssh の設定（`IdentityAgent`）が指すエージェントの鍵は `ok`。独自の ssh コマンドがあれば、鍵は判定しない。`git://` は `warn`。`ext::` の URL は実行しない。`github.com` の SSH 形式は HTTPS として確認する。`origin` 以外の名前のリモートが1つだけなら、それを使う。`remote.pushDefault` に従う。存在しないリモートを指していれば `warn`。detached HEAD を知らせる |
| 接続 | 読み取れるリモートは `ok`。取得用の URL は読めても、push 用の URL に接続できなければ `FAIL`。push 用の URL が2つあれば、両方を確かめる。存在しないリポジトリには、URL の確認を案内する。HTTPS を SSH に戻すホスト側の読み替えがあっても、HTTPS で接続する（ssh を起動しない） |
| 認証ヘルパーへの副作用 | 認証を拒否するサーバー（401）に対して、利用者のヘルパーには「取得」しか届かない。認証情報が保存されず、常駐プロセスも起動しない。認証の失敗として案内する |
| `gh`、VS Code の拡張 | `gh` が認証済みなら `ok`（トークンは表示しない）。必須の拡張がなければ `warn`。拡張の名前は大文字と小文字を区別しない。`code` が VS Code に接続できなければ `info` |
| 作業ツリー、ツール | 未整形のファイルは件数付きで `warn`。Ruff が構文を解釈できないファイルは、別の文言で `warn`。別の版のツールは `warn`、ツールがないと `FAIL`。`~/.local/bin` が PATH にないと `warn`。CRLF で登録されたファイルと、`core.autocrlf` が `true`・`yes` の場合は `warn` |
| Dev Container の外 | その旨を表示し、ツールがなくても `FAIL` にしない |
| オプション | `--quiet` は、問題がなければ何も表示せず、あれば、その区分の見出しと問題だけを表示する。不明なオプションは終了コード 2 |
| 制限時間 | 子プロセスが出力を握ったまま止まったコマンドを打ち切る。プロセスを残さない。標準入力を渡し、終了コードを保つ |
| 一時ファイル | 一時ディレクトリに何も残さない。一時ディレクトリを作れなければ、その旨の `FAIL` |
| リポジトリの外、所有者の不一致 | それぞれ、その旨の `FAIL` |

Dev Container の外（この検証環境）でも実行し、「ここは Dev Container の外（ホスト）です」と表示して、ツールの確認を省くことを確かめました。

## 敵対的検証での指摘と対応

検証は2回行いました。1回目は最初の実装（コミット `4569ca8`）、2回目は1回目の対応のあと（コミット `3552e8b`）が対象です。どちらも、フックと `make doctor` に分けて、別々の検証者に渡しました。渡したのは、対象のファイル、意図した仕様、イメージで試す手順です。実装者の検証結果は渡していません。2回目は、1回目の指摘と対応の一覧を「未確認の主張」として渡し、直っているかの確認と、設計の変更で新しく入った欠陥の発見を頼みました。どの検証者も、実際のイメージで再現した結果を報告しています。

### 1回目: フック（指摘10件）

最初の実装は、Git の設定（`core.hooksPath`）を、追跡しているディレクトリ（`scripts/git-hooks`）に向けていました。また、道具の版が `requirements.txt` と一致するかどうかで、検査をするかを決めていました。

| 指摘 | 対応 |
| --- | --- |
| `prek install` を実行すると、追跡しているフックが上書きされ、ホストでコミットできない状態に戻る | フックを `.git/hooks` にコピーする方法に変更。`prek install` は追跡しているファイルに触れなくなり、`make hooks` で元に戻る。`make doctor` が検出する |
| `requirements.txt` の版がイメージと違うだけで、コンテナ内の検査がすべて無効になる | 検査をするかどうかを、Dev Container の中かどうかで決めるように変更。版が違っても検査は実行する |
| `scripts/git-hooks` のないブランチでは、フックが何も動かない | コピーしたフックは、どのブランチでも動く |
| `make unhooks` を実行すると、以前の `prek install` のフックが復活して、ホストでコミットできなくなる | `make hooks` が、`prek install` のフックを置き換える |
| ホストに版の合う道具があっても、mypy が依存を見つけられないとコミットが止まる | ホストでは、道具の有無にかかわらず検査を省く。検査したい人だけが有効にする |
| `.git/hooks` にある他のフックが、黙って無効になる | `.git/hooks` をそのまま使うので、他のフックは動く。同じ名前のフックは退避して、`make unhooks` で戻す |
| ブランチをチェックアウトしただけで、そのブランチが足したフック用のファイルが、ホストで実行される | Git は、追跡しているディレクトリのファイルを直接は実行しなくなった |
| `requirements.txt` を読めないと、入っている版のまま検査が動く | 版による判定をやめたため、該当しなくなった |
| テストが甘い（道具の組み合わせを確かめていない、失敗の理由を見ていない） | 上の表の状態を追加。失敗は、`ruff format` の失敗であることまで確かめる |
| `make unhooks` の表示が、リポジトリの外などで誤っている | インストーラーをスクリプトに分け、状態に合わせて表示する |

### 1回目: make doctor（指摘16件と、軽微な指摘）

最初の実装は、認証ヘルパーの設定を自前で解釈し、署名を別の一時的なリポジトリで試していました。
